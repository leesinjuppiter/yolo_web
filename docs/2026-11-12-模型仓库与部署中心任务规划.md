## 1. 建议交付目标与范围

形成可追溯链路：
训练任务 → 注册模型版本 → 固定评估集上的独立评估 → 多模型对比 → 格式导出 → 产物精度/性能验证 → 部署包 → 指定目标机下发 → 运行验证 → 必要时回滚。

模型仓库回答“这是什么模型、依据什么认为它可用”；部署中心回答“哪个包被下发到哪台机器、是否真正运行、如何恢复旧版本”。

以下是建议，不把用户尚未确认的选项当作决定：

- 模型仓库纳管现有 detect / segment / obb / classify 四类训练结果；不新增 pose、tracking。
- 第一条可运行的导出链路优先 Detect/OBB + ONNX FP32；是否四类同时开放、是否必须 TensorRT FP16，等待确认。
- 首版部署支持下载包、单目标 SSH 冷切换、运行验证和失败回滚；灰度、无停机热切换、连续在线监控后置。
- 保持 PostgreSQL + 文件系统；不为这次引入 S3、Redis、Celery、Kubernetes。
- 当前租用 GPU 服务器可作为开发与流程测试环境；不能替代真实工控机或 Jetson 的兼容性、速度和稳定性验收。
- 新增一个最小推理执行程序，还是接入用户已有推理程序，必须确认目标机与程序契约后再确定。

用户笔记明确排除：Kubernetes、大规模调度、IoT 接入、多租户/完整权限体系、完整设备监控运维。笔记前文 RBAC、追踪、灰度等作为远期参考，不自动纳入首版。

## 4. 笔记与原型中需修正的工程判断

| 问题 | 建议 |
|---|---|
| experiment/candidate/validated/active/deployed 混为一条状态 | 生命周期、评估结论、平台推荐、部署运行状态分开；一个版本可同时推荐并部署多台机器 |
| “已测试”模糊 | 区分冒烟推理成功、完整评估完成、业务阈值达标；每个结果绑定数据/设备/配置 |
| 版本号直接从 vN 改为语义版本 | 保留旧标识；先确认“模型系列”如何分组，再决定每系列版本号；不自动把历史 v2 解释为 v2.0.0 |
| FP16 必然无损、INT8 必然更快 | 作为待实测假设；性能、精度需配对报告，INT8 首版不默认打开 |
| INT8 PTQ 被写成“动态量化” | 区分具体后端量化方式；校准数据与评估数据分离，拒绝自动拿演示默认数据集校准 |
| TensorRT engine 到处可运行 | 包含平台、架构、GPU、驱动/runtime 兼容条件；优先目标环境构建并验证 |
| batch=8，7.8ms per image，却标 1025.6 FPS | 每张 7.8ms 对应约 128.2 张/s；每批 7.8ms 才是约 1025.6 张/s，统计字段写明单位 |
| 1/forward 延迟等于流水线吞吐 | 分开记录 forward、预处理、后处理、主机/设备拷贝和完整请求；吞吐用处理总样本数/实测总时间 |
| TDP 当作模型实际功耗、称静态显存为峰值 | TDP 与实测功耗分开；没有采样数据不展示功耗效率；内存注明进程/设备、峰值/稳定态 |
| “漏检率降低即完全杜绝次品流出” | 删除绝对保证；模型指标不能直接推出分选/质检业务可靠性 |
| 0ms 停机、8ms 自动回滚 | 删除承诺；需要常驻推理服务、状态切换协议、资源余量和目标机实测 |
| ZIP + SHA-256 即防篡改身份认证 | 哈希用于完整性，签名用于来源认证；SSH 主机校验另做；若需数字签名须增加密钥与验签设计 |
| 部署包只有模型和脚本 | 补推理执行代码/适配协议、依赖锁定、运行环境要求、样例及预期输出；否则只有文件分发能力 |

官方依据：Ultralytics 的导出格式和参数有后端差异；TensorRT engine 兼容性有明确平台/版本/硬件条件；ONNX Runtime CUDA 还依赖匹配的 CUDA/cuDNN。实施时按项目实际锁定版本验证，不照搬在线文档中更新的参数名。
参考：[Ultralytics Export](https://docs.ultralytics.com/modes/export/)、[TensorRT Engine Compatibility](https://docs.nvidia.com/deeplearning/tensorrt/latest/inference-library/engine-compatibility.html)、[ONNX Runtime CUDA EP](https://onnxruntime.ai/docs/execution-providers/CUDA-ExecutionProvider.html)。

## 5. 数据与状态契约

### 5.1 建议持久化实体

按阶段新增，未进入阶段的不提前建空表。使用外键、不可变摘要与明确 JSON schema；不建设通用低代码任务平台。

| 实体 | 核心字段 | 约束 |
|---|---|---|
| model_versions（扩展） | 原有字段、display_name、description、lifecycle、可选 model_family_id | 原 ID、number、task_id、sha256 不变；权重/训练来源不可编辑 |
| model_families（若确认） | name、task_type、class_schema_digest、recommended_version_id | 推荐范围明确后才建；旧版本先不自动合并 |
| evaluation_snapshots | dataset_id、split、manifest_path、image/label/class digest、count、created_at | 数据及标签固定；同名数据集修改后必须新快照 |
| evaluation_runs | version_id、artifact_id、snapshot_id、protocol、runtime、status、metrics、report、error | 原模型/导出产物共用评估契约；保留指标来源与任务类型 |
| export_tasks | version_id、format、precision、input_spec、exporter_version、config_digest、status、logs | 重试新记录；不覆盖原权重 |
| model_artifacts | version_id、export_task_id、format、precision、hash、size、storage_key、compatibility、pipeline_digest | 导出完成后不可变；OpenVINO 等多文件作为一个清单 |
| benchmark_runs | artifact_id、target_fingerprint、runtime/provider、input/batch、timing_scope、iterations、raw_samples、summary | 同环境才做速度排序；性能失败不篡改精度结果 |
| comparison_reports | selected run/artifact IDs、baseline、comparability、snapshot payload | 固定引用和结论；后续新测试不覆盖旧报告 |
| deployment_packages | artifact_id、runtime_adapter_version、config_digest、manifest、hash、build_status | 已发布包不可原地修改；报告与运行配置一致 |
| deployment_targets | name、host、port、user、credential_ref、host_key_fingerprint、last_probe、capabilities、runtime_adapter | 不返回凭据；探测结果有时间戳 |
| deployment_tasks | package_id、target_id、previous_release_id、config、status、phase、timestamps、error、parent_task_id | 单目标互斥；执行与回滚分别留记录 |
| target_releases | target_id、package_id、config_digest、verified_at、release_path、state | 只在远端确认后更新 current；不因上传成功而更新 |
| events/logs | owner_type/id、sequence、time、event、safe_details | 游标查询；审计持久化且脱敏；不为首版新增完整全站审计 UI |

按现有任务模式复用日志/文件读写方式；是否复用物理日志表由迁移设计决定，不把训练日志强行混入新任务。

### 5.2 状态规则

- 生命周期建议：candidate → archived，可恢复；注册即 candidate。是否需要独立 experiment 见待确认项。
- 验证记录：not_run / queued / running / passed / failed / insufficient。执行成功与质量通过分开字段；没有门槛时只能“评估完成、待判定”。
- 推荐：独立指针，绑定明确模型系列/用途，不设“全平台唯一最佳模型”。
- 导出任务：queued → running → succeeded / failed / canceled；phase 分 export / load_check / write_manifest。succeeded 仅表示产物成功，不等于部署合格。
- 部署任务：queued → running → succeeded / failed / canceled / unknown；phase 分 precheck / transfer / checksum / stage / switch / verify / cleanup。
- 回滚任务：同样有执行状态，task_kind=rollback，引用 deployment_task_id；界面显示 rollback_running / rolled_back / rollback_failed 的关联结果。
- SSH 中断后的远端结果可能未知：保持 unknown，重新读取远端执行日志/版本指针确认；不盲目重复切换或报失败回滚。
- 无旧版本的首次部署失败：清理本次候选、恢复未部署状态并记录失败，不显示“回滚成功”。
- 归档不删除文件、不停止已有部署；归档版本不得默认用于新的推荐/部署，历史恢复仍可定位受保护旧包。
- 有任务、报告、部署或回滚引用的产物禁止物理删除；首版建议只归档。

### 5.3 可比性与放行规则

精度比较必须记录：任务类型、类别映射、冻结样本与标签、split、输入处理、模型/产物哈希、评估器版本、指标定义与必要参数。不同输入尺寸可作为明确的配置对比，但不能把差量归因于模型结构，需显示该变量。

性能比较必须记录：目标设备/架构、runtime/provider、版本、精度、输入尺寸、batch、并发、预热、次数、数据搬运/后处理是否计入。严禁将 CPU fallback 的结果标成 CUDA 性能。

建议每个指标返回 value、unit、sourceRunId、scope、availability；每组返回 comparable 和 reasons。缺失数据不是 0；baseline=0 时相对变化为 null。

默认部署门槛结构：加载成功 + PT/导出配对评估 + 指标阈值 + 目标兼容性 + 目标样例推理 + 资源/延迟限制。具体数值必须由用户指定。只做测试的部署应清楚标“测试用途”，不签发生产合格结论。

现有 50 张数据集用于链路测试；其 test 分集只有 10 张（按上一轮审计记录，实施前复核），不能支撑稳健的工业精度或漏检率结论。被修正的测试副本保留血缘和修改记录；不得当作完全未经处理的原始数据。

Detect/OBB 等任务的解码、评估与后处理优先复用已锁定版本的 Ultralytics 能力，通过实际 PT/导出产物对照验证；不自行另写一套旋转框评估或 NMS 算法。最小推理程序也需固定同一处理协议。

## 9. 部署包与目标执行契约

建议包结构（文本定义，不要求新增打包框架）：

- manifest.json：schemaVersion、modelVersionId、artifactId、hash、taskType、classesDigest、input/output、format/precision、runtime约束、构建环境、报告引用。
- model/：模型文件及关联外部数据文件、classes.json。
- config/：model_meta.json、preprocess.json、postprocess.json、runtime.json。
- runtime/：最小推理程序或对用户已有程序的固定适配器；说明输入输出、启动/停止/健康探测方式。
- environment/：锁定依赖与系统先决条件；是否包含离线 wheel/镜像取决于目标联网条件。
- scripts/：install、verify、activate、rollback；使用固定模板和参数，不接受任意 shell 字符串。
- verification/：获准分发的少量样例及预期检查；无授权不打包原始训练集。
- reports/：精度/性能/兼容性结果与条件；大体量预测数据保持外部受控引用。
- checksum.sha256：成员相对路径与 hash；自身不自包含；包文件 hash 由外部制品记录保存。

远端建议 releases/<package-id>/ + 当前版本指针 + 上一成功版本指针 + journal。先上传暂存目录、校验、安装/预检，再停旧启新、做真实推理、最后确认 current。原子替换指针只保证文件选择原子，不保证进程零停机。

回滚必须同时恢复模型、配置和所需运行环境。共享 Python 环境被新包升级后，单换 model.onnx 不能可靠回滚；建议每版本隔离依赖或严格不变的已验证 runtime。选择方式依赖目标机器存储/网络/权限。

最小运行契约必须支持：查询当前 releaseId、启动候选、健康检查返回 releaseId + runtime、对固定样例真实推理、停止指定版本、恢复旧版本。只返回 HTTP 200 或存在进程不够。

SSH 使用专用账号/密钥引用、固定目录、主机指纹、超时、输出脱敏；部署包解压拒绝绝对路径、..、越界符号链接。目标部署与回滚共用远端锁，远端持久化操作 ID，断连后可核对结果。

## 10. 验收与证据要求

### 模型仓库与对比

- 旧注册结果展示成功，ID/版本/来源/哈希不变；未评估仍未评估。
- 搜索分页、选择、归档、详情返回与浏览器刷新可恢复；动作权限由服务端校验。
- 不同类型不能混做统一 mAP 排名；分类、分割和 OBB 口径明确。
- 相同名称不同快照不可严格比较；多模型训练集与评估集重叠能提示/阻断独立结论。
- 提交重复不重复执行；取消、worker 退出、失败报告可查询。

### 导出与验证

- 至少一个 Detect、一个 OBB 真模型进行 PT→ONNX→实际推理→配对评估（以最终确认任务矩阵为准）。
- 坐标、角度、类别映射和原尺寸还原正确；NMS 差异有记录。
- 原权重不变、哈希可追溯、文件缺失和篡改能识别。
- 指定 GPU 却落到 CPU 必须明确失败或记录实际执行，不能冒充 GPU 测速。
- benchmark 保存原始时间样本、scope、batch单位、运行环境；不与训练同卡并行。
- 精度阈值未确认时不自动判“可生产部署”。

### 部署与故障注入

- 成功：包v1下发→校验→加载→样例推理→确认；v2替换成功，记录旧版本。
- 包损坏、类别文件不匹配、runtime不兼容：切换前拒绝，旧服务保持。
- v2启动/推理失败：恢复v1，并验证v1实际运行。
- v1本身缺失/恢复失败：明确 rollback_failed，附人工恢复步骤，不标成功。
- 断网/SSH断连：任务 unknown，重连核对远端日志，不重复激活。
- 首次部署失败：不谎报回滚；重复点击/重复请求/并发同目标有锁。
- 取消测试覆盖切换前与切换后两种边界。
- 回滚恢复配置与依赖环境；归档/删除操作不破坏回滚包。

### 页面与回归

- 1366/1440/1920 级桌面宽度检查，长 Diff 表横向滚动、操作区不遮挡；不按设计稿 2560px 固定宽度。
- 列表→详情→返回保持页码/筛选/滚动与已有数据；后台刷新失败不清空旧数据。
- 隐藏页暂停轮询，过期请求不得覆盖新查询；多个详情面板不得重复开轮询。
- 列表不依赖全量数据集与图片；实际测量返回交互与网络等待，不用一次脚本耗时宣称正式性能指标。
- 后端用独立 PostgreSQL 库，前端 typecheck/build；受影响训练注册、微调、恢复、列表返回功能回归。
- UI/API/模拟SSH测试与真实目标验收分开报告；本机SSH仅证明流程，不证明异构机器可部署。

| D06 | 是否需要 experiment 和人工 candidate 晋级 | 首版注册即 candidate，归档独立，验证由报告产生 | 决定状态机与审核动作 |
| D07 | “推荐”作用范围 | 同任务+类别体系+明确用途的模型系列 | 避免全平台最佳的歧义 |
| D08 | 评估集、业务门槛与关键类 | 用户指定固定评估集、最低指标、最大精度损失、P95和内存上限 | 阈值未确认只能出测试报告，不能签发生产放行 |
| D09 | 综合分、雷达图与自动推荐 | 首版不用加权总分；使用原始指标+明确门槛 | 无归一化/权重规则不能计算 91.4分 |
| D10 | 相机/RTSP/GigE/PLC/低置信度回流 | 本轮不做采集与业务控制，只验证文件/请求推理 | 若纳入，需要独立输入协议、丢帧策略与实时验收 |
| D11 | 包的在线/离线安装、完整依赖打包 | 目标可联网时锁定依赖；完全离线需额外制品 | 影响包体积、依赖分发与许可核查 |
| D12 | 签名、登录访问与公网暴露 | 首版可信内网/SSH隧道+凭据保护+SHA256；不宣称签名 | 若需公网多人，必须补最小认证/授权；仍不等于多租户 |
| D13 | PDF、批量导出、功耗评测 | JSON/CSV先做，批量格式任务/PDF/功耗另排 | 影响页面与测试工时 |
| D14 | 导出依赖环境 | 尽量独立Conda环境，锁定已验证版本，保持训练环境稳定 | 安装前单独列依赖并按用户授权执行 |

## 12. 开发交付与备份规则

- 先冻结 D01–D03 与影响当前阶段的边界；D04–D14 可按阶段确认，不让灰度等远期问题阻塞基础仓库。
- 每阶段交付数据库迁移、Tools/API、页面、测试证据和使用说明，不提交只有静态成功数据的页面。
- 代码按阶段或可验证的小任务提交；提交前查密钥/凭据、原始数据、训练权重与大文件。
- 及时推送用户仓库备份；训练数据、模型包、数据库、SSH凭据不进 Git；代码备份不等于数据备份。
- 已部署服务器工作树有此前上传代码，实施时先比较本地与服务器差异，不盲目 git pull/reset 覆盖运行环境。
- 本规划尚有待确认项，Git 中保存的是可审阅草案；不表示这些建议已获批准或已实施。
