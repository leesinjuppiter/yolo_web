## 3. 已确认的缺口与设计修正

### 3.1 提交端未拦截数据预检错误

`training/service.py:create` 已调用 `inspect_dataset`，但只检查 datasetName，没有拦截报告中的 errors。正常前端会先预检并拦截；直接调用创建接口或预检后数据变化，仍可能先进入队列，再由 worker 判失败。

建议：轻量可判定错误直接返回 422，附结构化 issues；文件、几何、深度重复检查继续在 worker 执行。这样减少已知无效任务入队，不把耗时扫描搬入请求。此结论来自静态路径检查，尚未做 HTTP 复现。

### 3.2 CPU 限制贯穿整个执行链

- `schemas.py`：`deviceId` 只接受 cpu，AMP 只接受 false。
- `catalog.py`：只提供 CPU；参数展开固定 AMP=false、workers=0。
- `runner_process.py`：设置 CUDA_VISIBLE_DEVICES=-1。
- `runner.py`：再次覆盖 device=cpu、AMP=false、workers=0。
- `worker.py`、`service.py`：环境与响应固定 CPU。
- 前端设备类型、标签和系统监控同样按 CPU 设计。

所以 GPU 接入必须同时修改配置、能力探测、进程环境、执行参数和展示。当前 Conda 中 CPU 版 PyTorch 也不具备 CUDA 执行能力。环境安装或替换另行征求用户授权，保留可用 CPU 环境。

### 3.3 微调已有基础，但缺少策略与模型来源扩展

`catalog.available_models` 已提供 YAML 从零训练和可信目录中四种固定文件名的预训练权重。因此不能称“完全没有微调能力”。缺口是显式初始化方式、冻结配置，以及选择平台已登记模型作为下一轮训练起点。

建议沿用 modelId，不再添加一个与其重复、可能冲突的 pretrained_model 字符串。模型选项补充来源类型和能力，后端依据真实模型来源推导初始化方式；前端用“从零训练 / 使用预训练权重”筛选，再选择模型。不要把单卡、多卡、冻结、恢复并列成 mode。

### 3.4 再次训练不等于恢复训练

现有 `retrain` 仅复制 config 并清空名称，不引用原 best.pt/last.pt。后端没有 resume 入口、父任务关系或检查点恢复检查。

建议保留“复制配置新建”，新增“使用此模型微调”和“恢复中断训练”两个明确动作。恢复产生新的执行记录，关联原任务，保留原终态、日志和产物。

### 3.5 单 worker 策略适合当前阶段

文件锁和 PostgreSQL 全局 advisory lock 限制同一队列只运行一个任务。单 GPU 接入可以继续串行，不需要立即改成每卡一个 worker，也不需要引入 Redis/Celery。

注意 `_recover` 会处理已有被认领任务。若将来开放多个 worker，必须先重做任务所有权和过期恢复条件，不能简单移除全局锁。

### 3.6 资源展示、模型管理和比较的边界

- 资源采样目前只有 CPU/内存，历史采样表主要保存在前端内存中；不能称为持久化 GPU 历史监控。
- 模型版本可以登记，但还没有完整模型列表、来源选择与独立评估模块。`validationStatus` 返回 unverified 是合理边界，应保留。
- `training_overview` 按任务类型计算平均指标，仍可能混合不同数据集/验证集；可作为列表统计，不能解释为模型总体能力或严格排名。
- 新建训练依赖全量 datasets/images；新增训练专用摘要接口即可减少耦合，不在本次重构整个标注页的数据获取。
- 表单默认 epochs=20、patience=50，早停通常无法在这个训练上限内发挥作用。提供提示或调整默认组合；不把学习率默认值直接宣称为适用于所有模型和数据。

## 4. 可执行任务清单

### T01 / P0：提交校验与基础回归

后端：在 `training/service.py:create` 拦截轻量预检 errors；保持幂等和重名规则；通过现有错误处理返回结构化信息。补充 `backend/tests/test_training_api.py` 等训练专项测试，使用独立 PostgreSQL 测试库。

前端：在 `api/training.ts` 解析字段/数据问题，在创建表单保留输入并显示原因；已存在的 warning 二次提交逻辑继续复用。

验收：直接 POST 无类别、无 train/val、任务不匹配的数据集不创建任务；预检成功后数据变坏再提交同样被拒绝；相同幂等键和配置只得到一个任务；合法 CPU 配置仍正常入队。

依赖：无。优先于增加训练模式。

### T02 / P0：配置分层与冻结微调

后端：扩展 `schemas.py`、`catalog.py` 和 `runtime.py`；增加有默认值的 freeze、workers 字段，保证历史 config 可读；模型目录提供初始化来源信息。先支持“不冻结 / 冻结前 N 个模块”，按模型实际结构校验范围。若添加“冻结 backbone”预设，必须提供受支持模型的映射和版本约束，不能假定永远等于 10。

前端：调整 `CreateTrainingDialog.vue`，基础项保留模型、数据、设备、epochs/batch/imgsz；优化器、学习率、workers、patience、freeze、seed 放入高级区域。`TrainingConfigPanel.vue` 同时展示请求值和实际值；补齐 `TrainingModel.pretrained` 等类型。

规则：从零训练默认不冻结，第一版可禁止这种组合；微调允许不冻结。冻结无效时明确拒绝，不能悄悄忽略。保持现有驼峰业务字段，通过 catalog 转为框架参数。

验收：旧任务和旧配置仍能显示；从零训练、不冻结微调、冻结微调能正确区分；运行时检查可训练参数及实际冻结模块；设置没有被 runner 强行覆盖。

依赖：T01。可在 CPU 上先完成策略验证，不被 GPU 环境准备阻塞。

### T03 / P0：单 GPU 执行与资源能力

后端：扩展现有 options 返回执行端设备能力和不可用原因；探测以 worker 所在训练环境为准。API 与 worker 同环境仍通过版本/心跳说明，不能把 API 可见设备当成执行承诺。修改 schemas、catalog、runner_process、runner、worker、service 中的 CPU 固定值，保留 CPU 回退选项但不静默切换。

第一版仅 CPU 或手动选择单张 GPU；继续全局串行。明确定义物理卡选择与子进程可见序号的映射，保存请求设备、实际设备与 GPU 标识。AMP 作为 CUDA 能力条件下的参数，CPU 保持关闭。启动时再次检查设备。

前端：修改设备类型和选择组件；移除固定 CPU 文案；显示执行端不可用原因、实际设备。资源面板增加 GPU 利用率/显存采样及时间，区分主机卡统计与训练进程统计；不可获得的数据显示未知。

错误处理：区分 CUDA OOM、CUDA 不可用、模型加载、数据和依赖错误；当前 CPU_MEMORY_EXHAUSTED 不能继续覆盖所有显存错误。

验收：原 CPU 路径不退化；支持环境上真实单卡短训练，日志、实际 device、GPU 占用相符；取消后无残留进程；错误设备不会静默转 CPU；串行任务不重叠。代码模拟只能验收参数路由，不能代替 GPU 真机验收。

依赖：T01、T02 的配置契约；GPU 真机和适配环境。安装依赖需事先授权，本规划不执行安装。

### T04 / P1：已登记模型用于下一轮微调

后端：在 `app/models` 增加最小列表/查询/来源解析服务和 Tools；训练模块调用模型模块公开能力，避免把全部逻辑继续堆进 training/service.py。先支持已登记版本和现有可信目录模型，不做任意 URL 下载市场。

保存 parent_model_version_id 等来源关系；校验权重 hash、任务类型和可加载性；训练启动时复制独立输入。新建模型引用增加新迁移，不改已经应用的 0008。模型来源记录必须受删除保护。

前端：模型选择区区分基础模型与已有训练版本；详情页增加“使用此模型微调”；展示来源版本和新数据集，保留“复制配置新建”独立动作。

验收：A 任务登记模型后，B 实际加载 A 的 best 权重并记录 hash/来源；类型不匹配或文件校验失败被拒绝；B 不覆盖 A 的产物；类别变化按受支持框架规则处理并记录，不直接冒充 resume。

依赖：T02。无需等待 GPU。

### T05 / P1：恢复中断训练

后端：增加 `training.resume` Tool 和 `POST /api/training/{id}/resume`；建立 resume_from_task_id、来源 artifact 和 hash 等关系；先只支持失败/取消且具有完整可恢复检查点的任务。重复提交需幂等，避免同时恢复同一来源导致误操作。

复用原输入快照，使用独立任务输出目录；若共享快照必须提供引用保护，否则先复制到新任务目录。恢复从原配置和 checkpoint 建立，不允许客户端任意重拼原训练设置。按已验证的 Ultralytics 版本维护可覆盖参数白名单。检查模型、优化器、epoch 和必要状态；当前 ZIP 结构检查不足以证明能够恢复。

进程硬终止可能打断写入；需检查 last.pt 完整性。成功训练后的权重不默认视为可恢复检查点。没有有效检查点时，返回原因并提供复制配置新建。

前端：详情页分开展示恢复、复制配置、使用模型微调；显示恢复起点、原任务和允许修改的字段；延续 epoch 的显示避免与新执行时长混淆。

验收：短训练完成至少一个检查点后中断，再恢复；验证 epoch/优化器等状态承接且不超出原计划；损坏或不完整 checkpoint 被拒绝；原任务状态、日志、产物不变；新任务取消仍正确清理进程。

依赖：T01、T02；与 T04 共用来源解析时应先冻结公共契约。真恢复测试独立于 GPU，可先 CPU 验证。

### T06 / P1：训练输入摘要与可比性提示

后端：通过现有 Tools 分层增加训练专用数据摘要，返回任务类型、类别数量、有效样本和 split 统计、revision；不返回每张图的完整标注。比较服务先依据训练快照/验证输入摘要、类别映射和评估参数判断可比性；不能只按 task 相同就认定可比。

前端：创建训练改用摘要；需要“调整分集”时再读取对应数据详情，保留现有标注页面行为。列表平均分加清晰口径，必要时取消跨数据集平均；后续两任务对比显示配置差异和不可比原因。

验收：训练选择接口不含全量图片标注；切换数据后预检重新生效；不同验证数据的结果明确标注；四类任务的指标不混用。

依赖：T01；可与 T04 在职责明确后分别实现。摘要与比较可以拆成两个小改动提交。

### T07 / P2：单机多 GPU

前置：确认确有多卡执行端及操作系统/驱动/PyTorch/Ultralytics 组合支持。当前 CPU 环境不能执行此项硬件验收。

后端：设备请求改为多卡集合并兼容旧 deviceId；一次分配完整集合；第一版仍全局只运行一个任务，先验证单个多卡任务，不同时引入多任务并发。要求固定正整数全局 batch 且可被卡数整除，这是平台第一版约束。验证父进程、DDP 子进程、日志聚合、rank0 指标及统一输出目录。

特别检查：当前 runner 自定义 Python 回调和离线配置是否在 DDP 派生进程内生效；不能假设单进程回调天然传递。必要时通过可验证的 torchrun 入口显式安装回调，仍由 runner 层封装。

前端：支持多卡选择、全局 batch 说明、各卡监控；不支持时显示环境原因。

验收：至少两卡真实训练；每轮只记录一组主指标；任一子进程失败会结束整组；取消后所有卡释放；产物只归档一份。不能用 device=[0,1] 的配置测试代替多卡验收。

依赖：T03 稳定。跨机器训练、每卡并发调度不包含在本项。

### T08 / P2：独立评估衔接

训练结束和模型登记目前不能自动标成“已独立验证”。后续增加 evaluation 模块及 Tools，明确模型 hash、评估数据快照、split、指标类型、框架版本和评估参数。先完成单模型独立评估，再开放严格模型比较。

前端区分训练过程验证、最优权重验证、独立评估；保留未验证状态，避免把训练页最新指标当成所有场景下的模型质量。

验收：每份评估可追溯到具体模型和数据；重评不覆盖训练原始记录；未完成评估的版本不自动改变为 verified。

依赖：T04；属于训练后的衔接范围，可单独排期，不阻塞 T02/T03。

## 5. 推荐实施批次

1. 第一批：T01 + T02。先让数据校验、初始化方式、冻结参数与旧配置兼容可靠；以 CPU 小样本验证，新增能力不依赖 GPU 安装。
2. 第二批：T03 + T04。打通单卡和已有模型微调。GPU 环境未具备时先完成 T04 与参数路由测试，明确硬件验收待完成。
3. 第三批：T05 + T06。恢复训练、轻量数据摘要与比较口径。
4. 第四批：有明确多卡需求及执行端后做 T07；按独立评估需求开展 T08。

不为本次需求先建设微服务、分布式任务系统、自动调参、自动显存规划、完整模板中心或主动学习 Agent。现有 PostgreSQL 队列、工具层、文件快照和轮询可继续支撑前几个批次。

## 6. 验收和改动边界

- 每项任务以最小改动完成，不迁移既有接口命名，不重构无关标注和导入模块。
- 按缺陷添加具有行为意义的回归用例；训练 API/事务测试必须使用独立测试库，不向工作数据写入测试样本。
- 每批执行前端类型检查和相应后端测试；页面行为更改还需实际浏览器检查。
- 第一次扩展执行路径后，四类已支持任务均需小规模真实回归；先以 detect 打通公共链路，不能据此声称其他类型已验收。
- 环境依赖记录与真实运行环境对齐；保留现有模型离线加载和禁止自动安装策略。
- 不以训练 smoke 的成功证明真实数据精度、吞吐量或工业分选效果。

本规划没有给出固定日期工期：现有训练模块缺少专项测试，多卡硬件未确认，直接承诺天数不可靠。每批完成后，以代码变更规模和实测结果细化下一批。
