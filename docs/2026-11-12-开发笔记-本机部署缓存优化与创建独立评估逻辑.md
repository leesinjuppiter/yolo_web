## 一、本机部署与图片缓存优化

### 1. 核心判断

本机部署可以减少公网传输等待，但把当前网页打包成 Electron EXE，不会自动消除图片解码和画布绘制开销。

对当前项目，优先顺序建议是：先建立本地 Web 性能基线，再优化本地图片读取、分级预览、预解码和画布重绘，最后根据交付需求选择桌面外壳。

Electron 使用 Chromium 渲染页面，浏览器中的页面性能问题仍需要相应优化。其桌面能力有价值，但应与图片处理链路的优化分别评估。参考：[Electron 官方性能指南](https://www.electronjs.org/docs/latest/tutorial/performance)。

### 2. 当前运行位置与已有缓存

记录时的开发测试版本采用以下分工：

| 内容 | 所在位置 |
|---|---|
| 数据库、原始图片、模型文件、训练、评估和导出任务 | 租用的 GPU 服务器 |
| 页面、标注画布和交互逻辑 | 使用者本机浏览器 |
| 预加载的图片响应 | 本机浏览器 HTTP 缓存 |
| 当前图及附近图片的解码结果 | 本机浏览器内存 |
| 生成后的侧栏缩略图文件 | 服务端数据目录 |

当前已实现：

1. 标注侧栏使用最长边 160 像素的缩略图，画布继续读取完整原图。
2. 原图和缩略图采用 `private, max-age=3600`，允许浏览器私有缓存一小时。
3. 当前图优先加载、解码；附近解码缓存最多三张，按约 128 MiB 的预算限制相邻大图。特别大的当前图仍需单独容纳，因此这不是整个页面总内存的硬上限。
4. 当前图和附近图片就绪后，按当前分集顺序逐张预加载后续原图。
5. 切图、切换分集或离开标注页时中止旧队列；随后优先准备新选中的图片，再从新位置继续。
6. 后续预加载使用浏览器 HTTP 缓存，不把全部原图的解码结果常驻内存。
7. 本地预加载成功记录属于当前标注会话中的状态，不能据此保证浏览器缓存永久存在。

以下为前序开发步骤的记录，本次整理文档未重新进行这些实验。

### 4. 必须区分下载缓存、解码缓存和绘制

切换图片的等待可以拆成：

1. 请求调度和文件读取。
2. 图片响应传输或浏览器缓存读取。
3. JPEG、PNG 等压缩图像的解码。
4. 画布准备、缩放、标注节点更新和绘制。

“后续图片已缓存”主要说明前面的数据准备工作已经完成，并不等于后面的解码和绘制耗时为零。当前代码已经调用 `HTMLImageElement.decode()`，不能把再次加入同样调用当作一项新的性能改进。参考：[MDN：HTMLImageElement.decode](https://developer.mozilla.org/en-US/docs/Web/API/HTMLImageElement/decode)。

以常见 RGBA 像素数据估算：

| 图像尺寸 | 单份像素数据理论占用 |
|---|---:|
| 4096 × 2168 | 约 33.9 MiB |
| 2048 × 1084 | 约 8.5 MiB |

这个计算不包含额外 Canvas、GPU 纹理、命中检测画布或其他副本，不能当作页面实际总内存。文件只有几 MB，也不意味着解码后只有几 MB。

### 5. 本机部署建议的优化顺序

#### P0：建立真实本地数据路径和性能基线

- 图片、派生预览图和图片服务都在本机，优先使用 SSD。
- 保留现有 Vue + FastAPI，通过本机 `localhost` 提供页面和接口，先验证体验。
- 本机原图已在磁盘时，不默认再复制一整份原图作为另一套缓存。
- 如果仅把网页打包成 EXE，但图片仍来自远程服务器，公网传输等待仍然存在。
- 不预先把 localhost HTTP 的全部开销当作主要瓶颈；应与实际解码、绘制耗时一起测量。

#### P1：增加用于标注浏览的中等分辨率预览图

建议评估三层图像：

| 层级 | 用途 |
|---|---|
| 小缩略图 | 侧栏图片列表，当前已实现 |
| 中等分辨率预览图 | 适应窗口、浏览整图、普通切图，尚未实现 |
| 完整原图 | 放大、检查小目标、边缘精细标注，当前画布使用此层 |

例如先验证最长边约 1600–2048 像素的预览，实际尺寸应结合视口和屏幕像素密度确定，不直接写死为所有场景的最终参数。

边界要求：

- 标注继续使用原始图像坐标保存。
- 训练、数据导出使用原始图片与对应标注。
- 放大检查细节时可以切换高分辨率或原图。
- 不以低清预览替代煤矸石边缘、细小异物的精细判断。
- 预览与原图切换后，需要验证框、多边形、旋转框与关键点位置一致。

生成预览的第一轮原型可以沿用现有 Pillow。只有批量生成确实成为瓶颈时，再比较 libvips/pyvips。libvips 提供 JPEG 加载时缩小的能力，但它相对当前实现的具体收益仍需本项目实测。参考：[libvips：JPEG 加载时缩小](https://www.libvips.org/API/current/ctor.Image.jpegload.html)。

#### P1：分别管理磁盘缓存和解码缓存

- 原图和可复用派生图由本地服务管理。
- 解码缓存优先覆盖当前图、下一张及少量附近图片，并按内存预算回收。
- 更远的图片保留压缩数据，结合浏览方向提前准备。
- 派生缓存使用图片内容标识或文件版本判断是否需要失效和重建。
- 页面显示的预加载完成状态，与“缓存仍可用”“解码已就绪”保持概念区分。

浏览器也可以通过 Cache API 或 OPFS 管理额外持久化数据；这不要求 Electron，但需要处理配额、回收、版本和安全上下文。在已有本地 Python 服务的前提下，优先评估由 Python 管理派生图目录，减少重复存储机制。参考：[MDN：Cache API](https://developer.mozilla.org/en-US/docs/Web/API/Cache)、[MDN：OPFS](https://developer.mozilla.org/en-US/docs/Web/API/File_System_API/Origin_private_file_system)、[MDN：存储配额与回收](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)。

#### P2：依据测量优化解码和画布

- 先测量主线程长任务、图片解码和首次绘制耗时，再决定是否引入 Worker。
- 如需在 Worker 中准备位图，可评估 `createImageBitmap()`；它支持裁剪及指定输出尺寸，但不预设一定比现有方案更快。
- 当前底图和标注处于同一 Konva Layer，可验证分离静态底图与交互标注是否减少重绘。
- 保留已有的底图、文字等非交互节点 `listening: false`，避免重复提出已完成的优化。
- 不盲目增加图层或降低像素密度；图层有额外内存开销，降低像素密度也可能影响细节显示。

参考：[MDN：Worker 中创建 ImageBitmap](https://developer.mozilla.org/en-US/docs/Web/API/WorkerGlobalScope/createImageBitmap)、[Konva 官方性能建议](https://konvajs.org/docs/performance/All_Performance_Tips.html)。

### 6. 桌面交付路线比较

以下“适合程度”是结合当前项目技术栈的建议，不是已经完成的迁移或性能测试结果。

| 路线 | 主要收益 | 主要代价与边界 | 当前建议 |
|---|---|---|---|
| 本地 Web + FastAPI | 最大程度复用现有系统，容易建立同条件基线 | 需要管理本地服务启动 | 优先验证 |
| Electron + 本地 Python 服务 | 桌面窗口、目录操作、进程管理、固定运行环境 | 图像链路仍需优化；增加桌面运行时和打包维护 | 确定桌面交付需求后评估 |
| pywebview + Python 服务 | 与已有 Python 技术栈较接近，可复用 Web 页面 | 需要检查 WebView 兼容性与打包效果 | 可做小原型比较 |
| Tauri + Python sidecar | 使用系统 WebView，桌面外壳通常较轻 | 增加 Rust 集成；Python 与训练依赖仍需处理 | 重视外壳体积且能维护 Rust 时考虑 |

Electron 可管理持久会话与缓存，也支持自定义协议处理本地资源；这些都需要实际设计接入。将前端打包，不等于 PostgreSQL、Python、PyTorch 和训练环境自动完成交付。参考：[Electron Session](https://www.electronjs.org/docs/latest/api/session)、[Electron Protocol](https://www.electronjs.org/docs/latest/api/protocol)。

pywebview 支持 Windows Edge Chromium 渲染；Tauri 使用系统 WebView，并支持把 Python API 服务打包成 sidecar。参考：[pywebview Web engine](https://pywebview.flowrl.com/guide/web_engine.html)、[Tauri 架构](https://v2.tauri.app/concept/architecture/)、[Tauri Sidecar](https://v2.tauri.app/develop/sidecar/)。

若未来支持远大于当前图片尺寸的超大图，可评估 OpenSeadragon + 图像金字塔/瓦片，按缩放级别读取可见区域。这会涉及标注交互和坐标映射的适配，不作为当前普通几千像素图像的第一优先级。参考：[OpenSeadragon](https://openseadragon.github.io/)。

### 7. 建议的对比实验

对比对象：现有本地 Web、本地 Web + 分级预览、Electron 中运行相同页面。

控制同一台电脑、同一批图片和标注、相同视口与像素密度。分别记录：

- 首次打开图片的耗时。
- HTTP 缓存命中后的切图耗时。
- 解码缓存命中后的切图耗时。
- 拖动、缩放和编辑标注时的帧耗时。
- 连续切图后的 CPU、内存及相关 GPU 占用。
- 当前图片请求与后台预加载是否互相影响。

使用中位数和 P95 比较，统计 Python、数据库和前端相关进程，避免只比较某一个窗口进程。原图坐标、导出数据和标注精度应与性能一起验证。

## 二、“创建独立评估”的现有逻辑

### 1. 这项功能在评估什么

对模型仓库中已经登记的模型版本，使用其来源训练任务冻结快照中的 `test` 分集，执行一次单独的模型验证，保存可追溯报告。

它与以下功能的含义不同：

| 功能 | 数据与目的 |
|---|---|
| 训练过程的验证指标 | 通常来自训练快照的 val 分集，用于观察训练过程和模型选择 |
| 创建独立评估 | 使用来源训练快照的 test 分集，在独立任务中评估已登记权重 |
| ONNX 导出的配对验证 | 比较 PyTorch 权重与 ONNX 产物在固定数据、预处理和协议下的一致性 |
| 生产验收 | 需要业务阈值、代表性数据、目标设备与现场条件，当前独立评估不自动完成此判定 |

这里的“独立”包含任务隔离和使用 test 分集，不自动代表外部数据验证、跨矿区泛化证明或工业现场合格。

### 2. 页面入口与提交配置

入口：模型仓库 → 模型记录的“详情与操作” → “创建独立评估”。提交成功后进入部署中心的“验证报告”任务详情。

当前界面只开放 Detect / OBB 的未归档模型。弹窗显示模型身份，允许调整输入尺寸，执行设备固定为 CPU。

请求示例：

```json
{
  "versionId": "已登记模型版本的 UUID",
  "deviceId": "cpu",
  "imgsz": 640
}
```

- 接口：`POST /api/evaluations`，成功受理返回 HTTP 202。
- 可携带 `Idempotency-Key`，用于防止同一提交因重复点击或重试而创建重复任务。
- 当前弹窗默认采用来源训练的 `imageSize`，缺省为 640。
- **待统一边界**：前端输入为 320–2048、步长 32；后端 Schema 为 32–2048，尚未显式约束必须为 32 的整数倍。
- 当前不能在弹窗中自由选择外部测试集、GPU、任意权重路径或检查点。

对应源码：[提交弹窗](../frontend/src/components/models/ModelActionDialog.vue)、[前端评估 API](../frontend/src/api/evaluation.ts)、[后端 API](../backend/app/api/evaluation.py)、[请求 Schema](../backend/app/evaluation/schemas.py)。

### 3. 创建任务阶段的校验

后端通过 `evaluation.start` 工具进入创建逻辑，在数据库事务中处理：

1. 校验请求类型和字段；额外字段不接受，`versionId` 必须为 UUID，设备只能为 CPU。
2. 若提供幂等键，先对该键加事务锁并查询旧任务。
3. 同一幂等键、相同配置返回原任务；同一幂等键、不同配置返回冲突。
4. 根据模型版本找到来源训练任务及登记的训练产物，不信任前端传入文件路径。
5. 检查权重文件存在、路径在来源任务目录内，并验证 SHA-256 与登记值一致。
6. 拒绝归档模型，拒绝非 Detect / OBB 类型。
7. 检查来源训练快照记录中存在 test 样本。
8. 创建等待执行的评估记录。

**创建成功仅表示任务被受理。**完整快照和数据重叠检查在后续执行阶段进行，因此收到 202 后仍可能执行失败。

对应源码：[评估服务](../backend/app/evaluation/service.py)、[模型来源与权重解析](../backend/app/models/sources.py)。

### 4. 排队和执行器调度

- 评估执行器按创建时间领取 queued 且未请求取消的任务，串行处理。
- 使用数据库 advisory lock 防止同一类评估执行器重复启动。
- 与模型导出任务共享模型计算锁，避免评估和导出同时占用这部分计算流程；训练或其他外部负载仍需另行考虑。
- 状态进入 `running` 后可能仍处于等待共享锁阶段，不能把 running 一概解释成已经开始推理。
- 常见阶段为等待、准备快照、执行评估，最终为 succeeded / failed / canceled。
- 执行器重新启动时，会把遗留 running 记录标为失败；当前不是自动从中断处恢复评估。

对应源码：[评估执行器](../backend/app/evaluation/worker.py)。

### 5. 测试快照如何冻结和防止明显的数据泄漏

执行器从来源训练任务的 `input` 目录读取训练快照，而不是从当前正在编辑的数据集重新随机划分。

检查过程：

1. 校验 `manifest.json` 的 SHA-256 与训练任务记录的快照摘要一致。
2. 根据 manifest 校验并读取样本清单。
3. 仅选择其中 `split == "test"` 的样本；没有 test 时失败。
4. 比较 test 与 train/val 样本的图片 SHA-256；存在字节完全相同的跨分集图片时拒绝执行。
5. 校验 test 图片和标签文件的路径、存在性与 SHA-256。
6. 把经过校验的 test 图片与标签复制到本次评估的独立输入目录，保存类别映射、样本清单及测试快照摘要。
7. 把登记权重复制为本次评估的 `model.pt`，再次校验复制后的 SHA-256。

注意：生成的评估 `data.yaml` 中，train、val、test 字段都指向独立评估目录的测试图片，这是为满足数据配置结构；实际调用显式指定 `split="test"`，不会因此执行训练，也不会重新使用原训练集。

**当前防泄漏能力的边界**：图片 SHA-256 检查能够发现文件字节完全相同的重复图，不能识别重编码同图、相邻视频帧、相似场景或同批次样本之间的统计相关性。需要严格泛化评估时，应在数据准备阶段按矿区、批次、时间或采集场景等分组划分。

对应源码：[评估快照](../backend/app/evaluation/snapshot.py)。

### 6. 实际模型调用与固定协议

执行器在单独的 Python 子进程中运行评估。该子进程不直接访问业务数据库，并通过 `CUDA_VISIBLE_DEVICES=-1` 及 `device="cpu"` 固定使用 CPU。

核心调用为 Ultralytics `YOLO(...).val(...)`，当前主要参数：

| 参数 | 当前值或来源 |
|---|---|
| 模型 | 本次复制并校验后的登记权重 |
| 数据 | 本次冻结的 test 快照 |
| `split` | `test` |
| `device` | `cpu` |
| `imgsz` | 本次提交的输入尺寸 |
| `batch` | 1 |
| `workers` | 0 |
| `conf` | 0.001 |
| `iou` | 0.7 |
| `plots` / `save` | false / false |

这里的 `conf=0.001` 是评估协议参数，不应直接当作生产告警阈值。数据在调用时仍会按 Ultralytics 的评估预处理规则处理，不等于把任意尺寸原图直接送入网络。

对应源码：[独立评估 runner](../backend/app/evaluation/runner.py)。

### 7. 报告内容、比较口径和页面更新

当前报告主要保存：

- Ultralytics 返回的整体指标，具体键以实际输出为准。
- 测试快照摘要、样本数、类别名称等信息。
- 评估协议及 `protocolDigest`：包括测试快照摘要、任务类型、输入尺寸、conf、iou、batch、评估器版本和 test 分集标识。
- 实际设备 `actualDevice="cpu"`。
- 本次模型权重的 `modelSha256`。
- 类别级 `map50_95`。
- `qualityStatus="not_assessed"` 及未设置业务阈值的说明。

报告成功写入后，执行器更新数据库状态，现有变化通知机制驱动相关页面读取最新状态；手动刷新和断线恢复继续适用。API 报告会去掉内部数据文件路径。

模型仓库当前取该模型最新创建的成功评估记录用于展示。模型对比要求所选模型都有报告，且 `protocolDigest` 一致，才计算可比较的指标差量；输入尺寸、测试数据、类别映射或评估器版本等差异都可能使其不可比较。

当前比较逻辑不是完整的生产验收体系，也不等于已经建立设备间性能排序。独立评估报告与 ONNX 导出的性能/配对验证报告需要分别理解。

对应源码：[报告与日志序列化](../backend/app/evaluation/repository.py)、[模型仓库及对比](../backend/app/models/registry.py)。

### 8. 取消和失败后的处理

| 情况 | 当前行为 |
|---|---|
| queued 阶段取消 | 设置取消标志并标记 canceled |
| running 阶段取消 | 设置取消标志；执行器检查后终止子进程并更新状态 |
| 权重或快照被修改 | 校验失败，不输出成功报告 |
| test 与 train/val 有完全重复图片 | 执行阶段拒绝作为独立评估 |
| 评估子进程失败 | 标记 failed，保留可查询错误信息和处理后的日志 |
| 执行器异常中断 | 遗留 running 任务在执行器重启时被标为 failed，需新建任务重试 |

运行中的取消是协作处理，不保证点击按钮后瞬时完成；若任务仍等待共享计算锁，也需要等待执行器进入相应处理流程。

### 9. 容易误解的边界与后续建议

- **数据集后来改了，不等于旧模型的测试集也改了。**当前评估复用来源训练快照，保持来源可追溯。
- **没有 test 分集，不会自动拿 val 顶替。**需要带独立测试集的训练快照；目前没有自由指定外部测试集的入口。
- **服务器有 GPU，不等于当前独立评估会用 GPU。**当前实现固定 CPU，不应把这些报告解释为 GPU 测试结果。
- **succeeded 表示评估流程成功结束。**`qualityStatus` 仍为 not_assessed，不代表满足业务精度阈值或允许上线。
- **有独立评估记录，不等于不同模型一定可公平排名。**必须核对同一测试数据与协议。

后续待确认事项：

- [ ] 统一前后端输入尺寸的范围与 32 整数倍约束。
- [ ] 是否允许为不同模型选择同一个固定、外部独立测试集；如支持，应继续冻结数据与类别映射。
- [ ] 是否需要按矿区、采集批次或时间分组的数据划分与近重复检查。
- [ ] 是否补充类别级 Precision/Recall、混淆矩阵和错误样本分析。
- [ ] 是否开放 GPU 评估；若开放，应明确设备、依赖版本和报告比较条件。
- [ ] 是否定义业务通过阈值与生产验收流程，并将“流程完成”和“业务达标”分开呈现。
